# Jobby

Jobby is a local-first job application tracker. It keeps applications, organizations, status changes, salary ranges, posting links, notes, and career-portal checks in a single SQLite database.

The application is intentionally designed for one person running it on their own machine. It has no accounts or authentication and should not be exposed directly to the public internet.

## Features

- Track open and closed job applications.
- Record salary ranges, work location, application dates, links, and notes.
- Move applications through applied, in-contact, accepted, and rejected states.
- Change an application's status directly from its summary.
- Track the last career-portal check using Today, Yesterday, and relative-day labels.
- Surface open applications due for a portal check using your chosen interval (seven days by default).
- Set your name and portal-check interval from Settings in the sidebar.
- Reuse organizations across applications and maintain their career-portal URLs.
- Store all data locally in SQLite.

## Technology

- Go standard-library HTTP server and server-rendered templates
- SQLite
- Goose migrations embedded into the application binary
- `sqlc`-generated database access code
- HTML, CSS, and JavaScript
- Docker

## Running with Docker

Build the image:

```sh
docker build -t jobby .
```

Run it with a persistent local data directory:

```sh
mkdir -p data
docker run --rm \
  --name jobby \
  -p 127.0.0.1:8080:8080 \
  -v "$PWD/data:/data" \
  -w /data \
  jobby
```

Open [http://localhost:8080](http://localhost:8080). The SQLite database is stored at `data/jobby.db` on the host.

## Running from source

The project requires Go 1.27 or newer.

```sh
go mod download
go run .
```

Open [http://localhost:8080](http://localhost:8080). When run from the repository root, the application stores data in `jobby.db`. Migrations run automatically at startup.

The listen address is currently fixed to port `8080`.

## Development

Format and verify the Go code:

```sh
gofmt -w main.go
go test ./...
go vet ./...
```

After changing a query in `db/queries` or a schema migration, regenerate the database package:

```sh
sqlc generate
```

Do not edit files in `internal/database` manually; they are generated by `sqlc`.

## Internal HTTP requests

Jobby does not expose a supported public API or command-line interface. The GUI submits HTML forms using `application/x-www-form-urlencoded` requests. This section documents that internal request contract for development and maintenance.

Application and organization mutations return `303 See Other` and redirect the browser to the relevant HTML view. Settings return `204 No Content` and the dialog reloads the current view.

### Settings

The sidebar Settings dialog saves your optional name and a portal-check interval of 1–365 whole calendar days. Settings are stored in SQLite and shared across this local workspace. Open applications become due when the days since their last check reach the interval; never-checked applications are always due. Changing the interval does not change existing check timestamps or weekly activity metrics.

`POST /settings` accepts `name` (up to 100 characters) and `portal_check_days`. It returns `204` on success or `422` for invalid values. The dialog reloads the current page after saving, preserving application filters.

The Settings dialog also includes **Hide salaries**, an immediate display preference remembered in the current browser. It masks salary amounts and editable salary fields without changing stored values. This is visual masking for screen sharing, not access control; values remain in the page data.

### Route summary

| Method | Path | Purpose | Success response |
| --- | --- | --- | --- |
| `GET` | `/` | Render the search overview | `200` HTML |
| `POST` | `/settings` | Save name and portal-check interval | `204` |
| `GET` | `/applications` | Render all applications with optional status, income, and organization filters | `200` HTML |
| `GET` | `/organizations` | Render the organization directory and editor dialog | `200` HTML |
| `POST` | `/organizations/{id}` | Update an organization | `303` to `/organizations?saved={id}` |
| `POST` | `/applications` | Create an application | `303` to `/` |
| `POST` | `/applications/{id}` | Replace an application's editable fields | `303` to `/#applications` |
| `POST` | `/applications/{id}/status` | Change only an application's status | `303` to `/#applications` |
| `POST` | `/applications/{id}/checked` | Set the last-checked timestamp to now | `303` to `/#applications` |
| `POST` | `/applications/{id}/delete` | Delete an application | `303` to `/#applications` |

Route IDs must be positive integers.

### Application fields

The create and full-update requests use the following fields:

| Field | Create | Update | Rules |
| --- | --- | --- | --- |
| `organization_name` | Required | Required | Whitespace is trimmed and collapsed. An organization is created or reused by name. |
| `careers_url` | Optional | Ignored | Complete `http://` or `https://` URL. When creating an application, a supplied value updates the reused organization. |
| `role_title` | Required | Required | Whitespace is trimmed and collapsed. |
| `status` | Ignored | Required | One of the status values listed below. New applications always begin as `applied`. |
| `work_location` | Required | Required | `remote` or `local`. |
| `posting_url` | Optional | Optional | Complete `http://` or `https://` URL. |
| `salary_min` | Optional | Optional | Non-negative whole-dollar amount. Both salary fields must be supplied together. |
| `salary_max` | Optional | Optional | Non-negative whole-dollar amount greater than or equal to `salary_min`. |
| `applied_at` | Optional | Optional | Date formatted as `YYYY-MM-DD`. |
| `notes` | Optional | Optional | Free-form text. |

Allowed application statuses are:

| Value | Meaning |
| --- | --- |
| `applied` | Applied and awaiting contact |
| `in_contact` | Actively communicating with the organization |
| `accepted` | Offer accepted |
| `rejected_after_contact` | Rejected after communication or interviews |
| `rejected_no_contact` | Rejected without direct contact |

The dashboard shows the five most recent `applied` and `in_contact` applications. The applications page includes all statuses.

### Create an application

`POST /applications` creates or reuses the named organization and creates an application with an `applied` status. The initial last-checked timestamp is set to the current time. The organization and application changes are committed in one transaction.

### Update an application

`POST /applications/{id}` is a full form update. Include every required field and every optional value that should remain on the record. Sending an optional field as empty, or omitting it, clears that value.

The editor preserves application-page filters when saving, including after a validation error.

Career-portal URLs belong to organizations and must be changed through the organization endpoint rather than this request.

Changing `status` also updates `status_changed_at`. Submitting the existing status leaves `status_changed_at` unchanged.

### Change only the status

`POST /applications/{id}/status` changes the status without resubmitting other application fields. Its body is limited to 4 KiB and `status` must be one of the documented values.

### Mark an application checked

`POST /applications/{id}/checked` has no form fields. It records the current UTC timestamp in `last_checked_at`.

### Delete an application

`POST /applications/{id}/delete` permanently deletes the application and has no form fields. It does not delete the associated organization.

### View and update an organization

`GET /organizations` renders the organization directory. Selecting a record opens its editor in a dialog. `POST /organizations/{id}` updates it using the `name` and `careers_url` form fields.

`name` is required and must remain unique without regard to case. `careers_url` is optional and must be a complete HTTP or HTTPS URL when supplied. Sending it as empty, or omitting it, clears the existing URL.

### Request limits and responses

- Application create, full-update, and organization-update bodies are limited to 64 KiB.
- Status-only request bodies are limited to 4 KiB.
- Application and organization validation failures return `422 Unprocessable Entity` with the form rendered as HTML.
- An invalid status-only request returns `422 Unprocessable Entity` as plain text.
- Missing or invalid IDs return `404 Not Found`.
- Unexpected database or server failures return `500 Internal Server Error`.
- State-changing requests reject a mismatched `Origin` header with `403 Forbidden`. Requests without an `Origin` header are accepted.

## Data and migrations

Jobby opens `jobby.db` relative to its working directory and enables SQLite foreign-key enforcement. It uses one database connection to keep access simple and predictable.

Goose migrations in `db/migrations` are embedded into the binary and applied automatically at startup. Application queries live in `db/queries`; `sqlc generate` turns them into the Go package under `internal/database`.

Timestamps are stored as UTC RFC 3339-style strings. Relative last-checked labels are calculated using calendar dates in the `America/Chicago` time zone.
